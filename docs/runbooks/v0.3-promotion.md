# v0.3 Calibration Revision — Promotion Runbook

Operator checklist for the Day-14 ship event that flips the scheduler from
shadow mode on Phase 1.5 to live mode on v0.3 calibration + tilt weights.

This runbook is the operational reference; it is not session-stamped. The
matching session journal entry (section 19.x in
`docs/sessions/2026-06-XX-full-session-journal.md`) records the actual ship
event — commit SHA, refit numbers, ship-criteria output — at execution time.

---

## When to run

After ~14 days of shadow data have accumulated. Check with:

```powershell
python scripts/shadow_status.py
```

Specifically, do NOT proceed until:

- Closed shadow predictions span **≥ 10 days** of post-validated cohorts.
- Total closed shadow rows are **≥ 2000** so per-bucket samples in the
  ship-criteria check are meaningful (target ≥ 20 per probability bucket).
- The `calibration_versions` breakdown in `shadow_status.py` confirms shadow
  rows were generated under Phase 1.5 (`1_5_4`) — i.e., no stale rows from a
  mid-window calibration swap.

If any of these are short, wait. Day-14 is a target, not a deadline.

---

## Step 1 — Pre-flight checks

- [ ] Scheduler is running and healthy:
      ```powershell
      Get-ScheduledTask -TaskName CryptoPredictorScheduler | Get-ScheduledTaskInfo
      ```
      `LastTaskResult` should be `0` and `LastRunTime` should be within the
      last 24h.
- [ ] `data/scheduler_config.yaml` is still on Phase 1.5 shadow:
      ```yaml
      mode: shadow
      calibration_version: "1_5_4"
      tilt_weights_version: "phase_1_5"
      ```
- [ ] Full test suite green:
      ```powershell
      python -m pytest -q
      ```
- [ ] Databases snapshotted (predictions.db is the source of truth for the
      validation loop and v1.0 tag criteria):
      ```powershell
      python scripts/backup_databases.py
      ```
      Snapshots land under `~/.crypto-predictor-backups/` by default; verify
      a fresh timestamped directory appears.

If any pre-flight check fails, **stop**. Diagnose and resolve before
touching the refit scripts.

---

## Step 2 — Run the refit scripts

Both refits read `predictions.db` and write versioned artifacts under
`data/`. They are pure, deterministic given the input data — safe to re-run.

- [ ] Calibration refit:
      ```powershell
      python scripts/refit_calibration_v03.py --shadow-weight 3.0
      ```
      Produces `data/calibration_0_3_0.json`. Default `--prior-alpha` and
      `--prior-beta` are both `1.0` (weak Beta(1,1) prior). Default
      `--shadow-weight` is `3.0` — shadow rows are weighted 3× backtest
      rows to reflect distributional currency.

- [ ] Tilt-weights refit:
      ```powershell
      python scripts/refit_tilt_weights_v03.py --shadow-weight 3.0
      ```
      Produces `data/tilt_weights_0_3_0.yaml`. This script does NOT take
      Beta-prior flags — smoothing happens inside the per-regime correlation
      step, not via a CLI knob.

- [ ] Review the `sign_changes` block at the top of
      `data/tilt_weights_0_3_0.yaml`. Each sign-flip relative to
      `data/tilt_weights_phase_1_5.yaml` must have a defensible regime story.
      Example of a justified flip:
      > "CHOP momentum tilt sign-flipped: shadow data shows trending
      > behaviour at the 4h horizon, not the mean-reverting pattern
      > Phase 1.5 was fit on."
      
      Example of a spurious flip that needs more data or stronger
      smoothing:
      > "TRENDING_BEAR funding tilt flipped from -0.04 to +0.01 — likely
      > noise; only 38 samples in this regime."

- [ ] If any sign-change looks spurious, re-run the calibration with a
      stronger Beta prior (the tilt-weights script has no equivalent
      knob — review samples-per-regime in the YAML and decide whether
      to wait for more data instead):
      ```powershell
      python scripts/refit_calibration_v03.py --shadow-weight 3.0 `
        --prior-alpha 5 --prior-beta 5
      ```

## Step 3 — Ship-criteria check

```powershell
python scripts/ship_criteria_check.py
```

This evaluates the last 7 days of closed shadow predictions against two
bars:

- **Headline**: hit rate ≥ 62.5% AND Brier ≤ 0.226.
- **Buckets**: every probability bucket with ≥ 20 samples must have
  |realized − expected| ≤ 10 percentage points. Buckets with < 20 samples
  soft-pass (logged but don't block).

Exit codes:

- `0` → message includes "✅ READY FOR PROMOTION" → proceed to Step 4.
- `2` → message includes "❌ NOT READY". Branch:
  - **Headline failed** (`escalation_recommendation: prior_alpha=5`):
    re-run the calibration refit with `--prior-alpha 5 --prior-beta 5`,
    then re-check. If still failing, escalate to an asof-guard audit —
    the look-ahead-bias hypothesis from the spec risk register is the
    leading candidate when calibration cannot reach 62.5% even with
    aggressive smoothing.
  - **Bucket failed** (`escalation_recommendation: manual_review_required`):
    manually inspect the flagged bucket. If the gap is on a low-sample
    bucket near the threshold, more shadow data may close it.
    Operator may decide to ship anyway based on judgment — document
    the rationale in the session journal entry before proceeding.

The script also prints a Telegram-formatted digest to stdout. If the
scheduler is set up with `telegram_chat_id_override`, the same digest will
arrive in the operator chat from the next scheduler run.

---

## Step 4 — Flip the config

Edit `data/scheduler_config.yaml`:

```yaml
mode: live                          # was: shadow
calibration_version: "0_3_0"        # was: "1_5_4"
tilt_weights_version: "0_3_0"       # was: "phase_1_5"
```

**Important**: keep the version strings quoted. YAML parses bare `1_5_4`
as the integer `154` (underscores as digit separators), which silently
breaks the loader.

Commit the change as the audit trail:

```powershell
git commit data/scheduler_config.yaml -m "ops(v0.3): promote to live"
```

Restart the scheduled task so the new config is picked up:

```powershell
Stop-ScheduledTask -TaskName CryptoPredictorScheduler
Start-ScheduledTask -TaskName CryptoPredictorScheduler
```

Confirm the restart by tailing the scheduler log; the next entry should
reference `calibration_version=0_3_0` and `tilt_weights_version=0_3_0`.

## Step 5 — Post-ship monitoring

- The next `predict_scan` (scheduled 06:00 UTC) will produce LIVE
  predictions (`mode='live'`) and the Telegram heartbeat will arrive
  WITHOUT the 🔬 shadow-mode prefix.
- The 3-of-7 auto-rollback (Task 8 — `should_auto_rollback` in
  `src/crypto_predictor/output/post_validation.py`) is now armed. If 3 of
  the first 7 live days come in under 50% hit rate, the validation job
  will:
  1. Flip `data/scheduler_config.yaml` back to `mode: shadow` and
     `calibration_version: "1_5_4"` / `tilt_weights_version: "phase_1_5"`.
  2. Send a ⚠️ AUTO-ROLLBACK Telegram alert with the offending daily hit
     rates.
- **Watch the first 3 live days manually.** The auto-rollback is a safety
  net, not a substitute for human review. Things to eyeball each morning
  for the first 3 days:
  - Heartbeat arrived, no missing-feature spikes.
  - Daily hit rate from `validate_pending` is ≥ 50%.
  - No new pattern blacklist hits, no calibration_version mismatch
    warnings.
- After 7 clean live days, log the cohort summary in the session journal.

---

## Step 6 — v1.0 tag criteria

After promotion, the v1.0 tag is earned when **all three** of the
following are true (see CHANGELOG and spec §risk register):

- 7 consecutive live days under v0.3 with hit rate ≥ 62.5%.
- The first drift alert (whenever it eventually fires) lands correctly —
  i.e., the alert reflects a real distributional change, not a false
  positive.
- ≥ 1 pattern v2 cohort has been classified SEEK or AVOID by the pattern
  layer (proves the pattern-v2 learner is producing actionable output,
  not just observations).

When all three land, tag `v1.0.0` and write a final session journal
section closing out the v0.3 → v1.0 arc.

---

## Rollback (manual)

If something looks wrong before auto-rollback fires, do not wait — flip
back yourself:

1. Edit `data/scheduler_config.yaml`:
   ```yaml
   mode: shadow
   calibration_version: "1_5_4"
   tilt_weights_version: "phase_1_5"
   ```
2. Commit:
   ```powershell
   git commit data/scheduler_config.yaml -m "ops(v0.3): manual rollback"
   ```
3. Restart the scheduled task:
   ```powershell
   Stop-ScheduledTask -TaskName CryptoPredictorScheduler
   Start-ScheduledTask -TaskName CryptoPredictorScheduler
   ```
4. Investigate:
   - `python scripts/shadow_status.py` — fresh look at the live cohort
     plus the resumed shadow stream.
   - `python scripts/ship_criteria_check.py` — what the bars say now.
   - `predictions.db` rolling-metrics query for daily hit rates by regime
     and bucket.
5. Document the rollback rationale in the session journal so the next
   refit cycle can address the root cause (look-ahead bias, regime
   misclassification, missing-feature spike, etc.).

If the auto-rollback already fired, the config is already on Phase 1.5
shadow — the investigation steps above still apply, and the next refit
should weight the failed live cohort accordingly.
