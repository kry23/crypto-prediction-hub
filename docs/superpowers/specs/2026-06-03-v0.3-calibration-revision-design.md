# v0.3 Calibration Revision — Design Spec

**Date**: 2026-06-03
**Status**: Brainstorming complete, awaiting user spec review
**Trigger**: First live cohort (2026-06-03) closed at 32.8% hit rate vs backtest baseline 62.5% — see `docs/analyses/2026-06-03-first-live-observation.md`.

## Goal

Bring live hit rate from the observed 32.8% back to ≥ 62.5% baseline by addressing five compounding root causes:
1. Calibration anti-correlation above p = 0.55 (higher confidence → worse outcomes)
2. Isotonic regression upper-tail saturation (CHOP ceiling at 0.9198)
3. Per-feature-availability blindness (sentiment + global NEUTRAL cohort mixed into the live distribution)
4. Possible stale per-tilt weights (Phase 1.5 fit may need data-driven re-evaluation)
5. No safe environment to iterate without sending false Telegram alerts to the user

## Architecture overview

Two ship vehicles in sequence:

- **v0.2.1 — Shadow infrastructure** (~1 day): scheduler runs in `mode=shadow`, persists every prediction with `mode`, `feature_completeness`, `missing_features` columns. Markdown report + Telegram heartbeat clearly marked shadow. Builds the safe iteration loop.
- **v0.3 — Calibration revision** (~5–7 days, ~14 days after v0.2.1 to let shadow data accumulate): beta-binomial smoothing on isotonic knots, linear tail extrapolation, per-completeness calibration maps, data-driven per-tilt re-fit, shipping-criteria gate, recency-weighted training. Promotion via `data/scheduler_config.yaml` edit.

Both vehicles share a single source-of-truth config file `data/scheduler_config.yaml` and a single predictions database with the new `mode` column.

### §3 Feature completeness detection

def detect_feature_completeness(

    global_features: dict[str, float] | None,

## v0.3 — Calibration revision

Triggered ~14 days after v0.2.1 ships, once shadow data accumulates.

### §1 Beta-binomial smoothing on isotonic knots

`src/crypto_predictor/calibration/beta_binomial.py`:

```python
def smooth_isotonic_knots(
    x: list[float], y: list[float], n_per_knot: list[int],
    *, prior_alpha: float = 1.0, prior_beta: float = 1.0,
) -> list[float]:
    """Pull each knot's y toward the prior 0.5 by effective sample size.

    Formula per knot:
      y_smooth = (n * y + alpha) / (n + alpha + beta)

    With Beta(1, 1) prior, knots backed by few samples regress strongly toward 0.5;
    knots backed by many samples retain their empirical y.
    """
```

Default `Beta(1, 1)` (uniform prior, weak pull toward 0.5). Aggressive variants:
- `Beta(5, 5)` — moderate pull, used in the first ship-criteria fail escalation (see §6)
- `Beta(10, 10)` — strong pull, used in the second escalation

### §2 Linear tail extrapolation past highest knot

`src/crypto_predictor/calibration/tail_extrapolator.py`:

```python
def extrapolate_upper_tail(
    x: list[float], y: list[float], *, target_x: float, cap: float = 1.0,
) -> float:
    """Linear extrapolation past the highest knot.

    Slope = (y[-1] - y[-2]) / (x[-1] - x[-2])
    Predicted = y[-1] + slope * (target_x - x[-1])
    Returns min(predicted, cap)
    """
```

Used at runtime: when `direction_raw` exceeds highest knot's `x`, instead of clipping to `y[-1]`, extrapolate. Cap at 1.0 to keep probabilities valid.

### §3 Combined runtime: fit → smooth → re-fit → persist → extrapolation at predict

**Fit-time pipeline** (in `scripts/refit_calibration_v03.py`):

1. Fit isotonic regression on raw `(direction_raw, outcome)` data → initial knot list `(x_i, y_i)`
2. For each knot, compute `n_i` = number of input samples whose `direction_raw` falls in segment `[x_i, x_{i+1})`
3. Apply beta-binomial smoothing to each knot: `y_smooth_i = (n_i * y_i + alpha) / (n_i + alpha + beta)`
4. **Re-fit isotonic** on `(x_i, y_smooth_i)` weighted by `n_i` to restore monotonic-non-decreasing invariant (smoothing alone can break monotonicity when low-`n` knots get pulled toward 0.5 more than high-`n` knots adjacent to them)
5. Persist the re-fitted map to JSON

**Predict-time** (in `src/crypto_predictor/calibration/isotonic.py` or new module):

1. If `direction_raw <= max(x)` → apply isotonic from persisted JSON (in-domain interpolation)
2. If `direction_raw > max(x)` → linear tail extrapolation per §2 (out-of-domain extension)

Why this order matters:
- Smoothing must precede re-fit, not follow it (smoothing on a monotonic curve produces non-monotonic intermediate; re-fit restores invariant)
- Tail extrapolation operates at predict time, not at fit time, because we don't know the predict `x` values in advance and we want them capped at 1.0 dynamically
- Tied-knot ceiling (current CHOP 0.9198 problem): smoothing pulls low-`n` knots toward 0.5; re-fit then redistributes the smoothed values. After this pipeline, ties at the ceiling become a graduated upper-tail. Linear extrapolation on this re-fit curve produces meaningful values past the highest knot rather than horizontal extension

JSON schema extension:

```json
{
  "fit_window": "...",
  "by_completeness": {
    "full": {"BULL": {...}, "CHOP": {...}, "BEAR": {...}},
    "degraded": {"BULL": {...}, "CHOP": {...}, "BEAR": {...}}
  },
  "smoothing": {"prior_alpha": 1.0, "prior_beta": 1.0},
  "extrapolation": {"cap": 1.0}
}
```

### §4 Data-driven per-tilt re-fit

`scripts/refit_tilt_weights_v03.py`:

```python
def diagnose_and_refit_tilts(
    *, backtest_data: pd.DataFrame, shadow_data: pd.DataFrame,
    shadow_weight: float = 3.0,
) -> dict[str, dict[str, float]]:
    """Per-tilt × per-regime correlation analysis + recency-weighted refit.

    Algorithm:
      1. Concatenate backtest_data (weight=1) + shadow_data (weight=shadow_weight)
      2. For each tilt × regime, compute weighted Pearson correlation with realized return
      3. Compare sign with Phase 1.5 weights. If sign flips → record audit entry.
      4. Re-fit per-regime weights using weighted least squares
      5. Emit YAML with weights + sign_changes audit log

    Returns: {regime: {tilt_name: weight, ...}, 'sign_changes': [...]}
    """
```

**Recency weighting rationale**: shadow data is the corrective signal (we know live model is broken). Backtest data is older but provides volume. `shadow_weight = 3.0` default; tuned in ship-criteria escalation if results are unstable.

### §5 Shipping criteria + escalation path

`scripts/ship_criteria_check.py`:

```python
def check_ship_criteria(
    *, shadow_predictions: pd.DataFrame,
    new_calibration_path: Path,
    new_weights_path: Path,
    min_samples_per_bucket: int = 20,
) -> ShipCriteriaResult:
    """
    Bar 1 (MANDATORY):
        7d rolling hit rate >= 62.5%
        AND
        7d rolling Brier <= 0.226

    Bar 2 (WARNING-LEVEL):
        For every p-bucket in [0.50, 0.55), [0.55, 0.60), ..., [0.80, 0.95):
        If bucket has >= min_samples_per_bucket: realized hit rate within ±10pp of expected (mean p).
        If bucket has < min_samples_per_bucket: not checked (insufficient evidence).

    Returns: ShipCriteriaResult(can_ship, warnings, escalation_recommendation, details)
    """
```

**If Bar 1 fails**, escalate by re-running calibration fit:
1. **Escalation 1**: re-fit with `prior_alpha=5, prior_beta=5` (moderate aggressive smoothing). Re-run check.
2. **Escalation 2**: re-fit with `prior_alpha=10, prior_beta=10` (strong smoothing). Re-run check.
3. **Escalation 3**: pause v0.3 ship. Audit asof guards in `FeatureFetcher` for look-ahead bias (the backtest 62.5% baseline may be fictitious). Brainstorm v0.3.1 alternatives (Platt scaling, extended fit window).

**If Bar 1 passes but Bar 2 has > 2 bucket warnings** (with adequate samples), Telegram-flag the user with bucket-level details and require manual approval before promotion.

### §9 Promotion workflow

1. Day ~14 of shadow: shadow data sample count crosses 4000+ AND first-shadow-week post-validation digest sent
2. Run `python scripts/refit_calibration_v03.py --shadow-weight 3.0` → produces `data/calibration_0_3_0.json`
3. Run `python scripts/refit_tilt_weights_v03.py --shadow-weight 3.0` → produces `data/tilt_weights_0_3_0.yaml`
4. Review `sign_changes` in the YAML — confirm none are spurious
5. Run `python scripts/ship_criteria_check.py --calibration data/calibration_0_3_0.json --weights data/tilt_weights_0_3_0.yaml` → Telegram digest
6. If ✅: user edits `data/scheduler_config.yaml` (mode=live, both versions=0_3_0), commits to git (audit), restarts scheduler
7. Post-ship monitoring (§risk register, post-ship rule) is now active

### §10 Post-ship monitoring rule

After v0.3 ship to live, the rolling post-validation digest watches for catastrophe:

> **If 3 of the first 7 live days under v0.3 close with hit rate < 50%, auto-rollback to shadow mode and send a Telegram alert.**

Implementation: `_job_validate_pending` after Telegram digest checks the rolling 7d window. If condition met:
1. Set `mode: shadow` in `data/scheduler_config.yaml` programmatically
2. Send Telegram alert: `⚠️ v0.3 AUTO-ROLLBACK — 3/7 days under 50%, reverted to shadow mode. Review and adjust before re-promotion.`
3. Future scans run in shadow mode until user manually re-promotes

This addresses the §risk-register concern that v0.3 might pass ship criteria but fail in live, and provides a safety net while allowing autonomous operation.
